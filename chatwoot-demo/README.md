# Chatwoot 演示套件（零域名 · 零备案）

给"初期只是演示、不上生产"用的最小可执行方案：**不需要域名、不需要备案、不需要买证书**。

客户入口是一个自带客服气泡的网页（冒充官网），用 IP 就能访问；坐席在 Chatwoot 后台接待，AI 话术助手和自动回复机器人照常工作。

```
┌──────────────┐  点右下角气泡    ┌────────────────┐
│  客户（演示页）│ ───────────────▶ │  Chatwoot 坐席台 │
│  http://IP:8081│                 │  http://IP:3000 │
└──────────────┘ ◀─────────────── └────────────────┘
        ▲                                   ▲
        │ 回复                              │ 生成建议 / 自动回复
        └───────────────────────────────────┴── 8787 话术助手 · 8788 机器人
```

## 文件说明

| 文件 | 作用 |
|---|---|
| `index.html` | 演示页（假官网 + 右下角 Chatwoot 气泡）。自动把 Chatwoot 地址指向「同一主机名:3000」 |
| `serve.js` | 静态服务器（零依赖），默认 **8081**，避开常见的 8080 占用 |
| `preflight.js` | 演示前自检：Chatwoot / widget / 演示页 / 可选组件 & 该填的地址 |
| `e2e.js` | 端到端验证：模拟客户发一条消息，确认真的落进坐席收件箱（`--clean` 验证后自动删掉这条测试会话） |

## 演示前 3 分钟清单

```bash
cd C:\Users\Administrator\Desktop\chatwoot-demo

# 终端 A：起演示页
node serve.js

# 终端 B：自检，全绿就能开演
node preflight.js

# 想确认"客户发的消息坐席真能看到"，再跑一次端到端验证
node e2e.js          # 加 --clean 则验证完自动清理测试会话
```

自检会告诉你本机所有可用地址（`http://192.168.x.x:8081`），并检查演示前必须确认的那一项（见下）。

## 演示动线（照着念就行）

1. **客户侧**：浏览器打开 `http://<本机IP>:8081/`，点右下角气泡，发一句"我昨天下的单，什么时候能发货？"
2. **坐席侧**：另一个窗口打开 `http://<本机IP>:3000/app/accounts/1`，看到新会话进来 → 点开
3. **秀 AI**：右侧 Dashboard App「DeepSeek 话术助手」→ 生成建议 → 会显示命中知识库的依据（📚 知识库参考）→ 复制发出
4. **客户侧**：气泡里收到回复，闭环完成
5. **可选**：让 8788 机器人先自动回一轮，再人工接管，展示"机器人 + 人工"协同

## 换一台机器演示时，唯一必改项

演示页会自动指向「打开它的那台主机的 3000 端口」，但 **Chatwoot 自己对外宣告的地址（`api_host`）来自 `.env` 的 `FRONTEND_URL`**。

```env
# Desktop\chatwoot-local\.env
FRONTEND_URL=http://192.168.5.106:3000
```

改完重启：

```bash
cd C:\Users\Administrator\Desktop\chatwoot-local
docker compose up -d chatwoot sidekiq
```

`preflight.js` 与 `e2e.js` 都会自动检测这个值是否"只对本机有效"，不用自己记。

## ⚠️ 坐席端"看不到消息"的两个原因

这是演示时最容易卡住的地方，按顺序查：

### ① 消息压根没发出去 —— `FRONTEND_URL` 指向 `localhost`

widget 下发给浏览器的 `api_host` 就是 `FRONTEND_URL` 的复刻。当它是 `localhost` 时：

- **本机上**打开演示页 → 请求发给本机 3000 → 看起来正常
- **别的设备（手机/另一台电脑）**打开演示页 → 气泡把请求发给**那台设备自己的 localhost:3000** → 那里什么都没有 → 消息永远发不出去

所以症状是"气泡能弹出来、能打字"，但坐席端一条都收不到。`e2e.js` 第一项检查就会点出来。

### ② 消息发出去了，但列表没显示 —— 新会话是 `pending` 且未分配

Chatwoot 里新会话默认状态是 **Pending**（等坐席响应），并且**未分配给任何人**。坐席端列表如果筛选停在：

- 状态 = `Open` → 看不到 pending 会话
- 分组 = `我的` → 看不到未分配的会话

把状态切到 **Pending** 或 **全部**、分组切到 **所有**，会话就出现了。

> 查数据库时注意 Chatwoot 的状态枚举是 `open=0, resolved=1, pending=2`（不是按字面顺序），别把 `2` 当成 resolved。
> 用 `e2e.js` 可以一步确认：它会发一条消息、再从坐席视角回查，直接告诉你 `status=... 消息 N 条`。

## 排错

| 现象 | 原因 / 处理 |
|---|---|
| 气泡不出来，左下角提示红色 ⚠️ | Chatwoot 地址不对。用 `?cw=http://IP:3000` 手动指定试试：`http://IP:8081/?cw=http://IP:3000` |
| 气泡出现、能发出去，但**坐席端看不到** | 见上一节两个原因。先用 `node e2e.js` 定位是"没发出去"还是"列表没显示" |
| 气泡出现但发消息报错 | 检查 Chatwoot 收件箱是否为「网站」类型且已启用 |
| 别人电脑打不开演示页 | 安全组/防火墙放行 8081；确认用的是局域网 IP 而不是 127.0.0.1 |
| 自检说「端口被其他服务占了」 | 你原来的 8080 测试页在跑，换端口：`PORT=8090 node serve.js` |
| 改了 `FRONTEND_URL` 还是老样子 | 容器要重建才吃新环境变量：`docker compose up -d chatwoot sidekiq`；浏览器再硬刷新一次清掉缓存的 widget 配置 |
| 话术助手显示 refs 为空 | 那是旧镜像，重建：`docker compose up -d --build`（见 chatwoot-deepseek-suggestions/README） |

## 为什么不用域名也能演示

- **非 80/443 端口不受备案限制**：`IP:8081`、`IP:3000` 直接可用，安全组放行即可
- **Web Widget 是嵌到你自己页面里的**，天然不依赖域名
- 只有"微信真实回调"才必须 80/443 + 域名，那属于**上线**阶段的事

## 什么时候必须升级到正式方案

只要满足下面任一条，就该走「域名 + 备案」：

- 演示对象在**公网**，且不想暴露 IP:端口
- 要对接**微信公众号 / 微信客服**（回调只接受 80/443）
- 要让客户用 HTTPS 访问（浏览器对 IP 的 http 页面会标"不安全"）
- 要长期运行、给真实客户用

升级路线见上一级目录的 `chatwoot-aliyun\README.md`（域名、免费证书、Nginx 443、安全组）。
